9월 15일에 JDK 27이 출시되었습니다. 비LTS라 운영에 올릴 버전은 아니지만, 이번 릴리스에는 뒤집히지 않는 한 다음 LTS인 29에도 그대로 갈 기본값 변화가 둘 들어 있습니다. G1이 모든 환경의 기본 GC가 되고(JEP 523), 압축 객체 헤더가 기본으로 켜집니다(JEP 534). 27을 쓰지 않더라도 결국 맞이할 변화라, 그 전에 제가 맡은 저장소 세 개가 지금 어떤 상태인지 정리해 두고 싶었습니다.

정리는 지난달에 시작했습니다. 8월 20일 Spring이 취약점 91건을 한 번에 공개했을 때, 어느 Boot 버전이 수정된 Security를 관리하는지 보려고 spring-boot-dependencies POM을 네 개 열었습니다. 4.0.7은 Security 7.0.6, 4.0.8은 7.0.7. 패치 번호 하나가 취약과 수정을 갈랐고, 제 서비스들은 그 라인이 아니라 3.5와 2.7이었습니다. 다음 CVE 때 또 손으로 할 생각이 없어서 저장소를 읽기만 하고 고치지는 않는 도구를 만들었고, 이 글은 그 도구로 JDK 27 주에 세 저장소를 돌린 기록입니다. JDK 27은 계기였고, 글의 대부분은 도구가 버전을 잘못 읽은 이야기입니다.

## Dependabot이 있는데 왜 만들었나

Dependabot과 Snyk 무료 티어는 의존성 버전이 취약 범위에 있는지까지 봅니다. Snyk 유료에는 도달 가능성 분석이 있지만 저장소 셋에 붙이자고 살 물건은 아니었고, 제가 필요한 건 그 옆의 두 가지였습니다. 하나는 JVM 플래그, 에이전트, `sun.misc.Unsafe` 사용처처럼 JDK 27 기본값 변화가 실제로 건드리는 지점입니다. 의존성 도구는 여기를 보지 않습니다. 다른 하나는 "버전이 취약 범위인가"가 아니라 "그 취약한 기능을 쓰는가"입니다. 8월 20일의 CVSS 9.4짜리는 Spring Security의 내장 LDAP 서버 문제였는데, 제 저장소 셋 중 내장 LDAP를 쓰는 곳은 없습니다. 버전만 보고 CRITICAL을 내는 도구는 운영자가 한두 번 확인한 뒤 열지 않게 됩니다.

규칙을 데이터로 두었습니다. CVE마다 취약 버전 범위와 함께 "사용 흔적 문자열"을 적습니다. 내장 LDAP이면 `UnboundIdContainer`나 `spring-security-ldap`, Tomcat 보안 제약 우회면 web.xml의 `<security-constraint>` 같은 것들입니다. 버전이 범위 안이고 흔적이 소스·빌드·설정 어디에도 없으면 심각도를 INFO로 내리고 "취약 버전이나 사용 흔적 없음"이라고 쓰고, 흔적이 있으면 원래 심각도에 발견한 파일을 붙입니다. 이 근사가 틀리면 소리 없이 틀립니다. 리플렉션이나 프로퍼티로 켜지는 기능은 문자열 흔적 없이 활성화될 수 있고, 그러면 INFO로 내려간 채 취약한 상태가 됩니다. INFO로 내릴 때는 무엇을 찾았는지 흔적 문자열 목록을 같이 적어, 검토자가 정의의 빈틈을 볼 수 있게 했습니다.

첫 버전은 Python으로 이틀 만에 썼습니다. 규칙 파일 스키마 검증이 없어서 필드를 빼먹으면 판정 도중에 KeyError가 났고, 이걸 자바 백엔드 팀이 고쳐 쓰려면 결국 자바여야 했습니다. Java 21로 다시 쓰면서 `Rules` 레코드의 컴팩트 생성자에 `Objects.requireNonNull(cves, "cves가 없습니다")`를 걸어 두니 필드가 빠지면 로딩 시점에 죽습니다. 규칙 파일을 손으로 고치다 필드를 빼먹는 일이 그 뒤로도 두 번 있었는데, 둘 다 실행 전에 걸렸습니다.

## 빌드 파일만 보면 라인은 맞고 패치는 틀립니다

도구가 처음 틀린 곳은 CVE가 아니라 버전 읽기였습니다. 스캐너는 빌드 파일을 정규식으로 읽습니다. Gradle이나 Maven 파서를 물리면 DSL 변형마다 깨지기 때문에 일부러 그렇게 했습니다. Spring Boot 프로젝트의 빌드 파일에는 보통 Boot 버전만 있고, Security나 Tomcat 버전은 BOM이 정하므로 파일에는 없습니다. Boot 버전으로 BOM 표를 찾아 채우는 방식을 썼고, 표에 없는 패치는 같은 라인의 가까운 아래 버전으로 "추정"이라고 표시했습니다.

이번 주에 `gradle dependencies` 출력을 읽는 옵션을 붙이고 같은 저장소를 다시 돌렸더니 이렇게 나왔습니다.

| 항목 | 빌드 파일 추정 | 해석 결과 |
|---|---|---|
| Spring Boot | 2.7.3 | 2.7.18 |
| Tomcat | 9.0.65 | 9.0.102 |
| Spring Framework | 5.3.22 | 5.3.31 |

라인은 다 맞았고 패치 번호는 전부 틀렸습니다. 서른여섯 개 모듈 중 일부는 플러그인에 2.7.18을, 일부는 의존성에 2.7.3을 직접 적어 두고 있었고, 스캐너는 가장 오래된 쪽을 대표로 잡았습니다. 런타임 클래스패스는 2.7.18. Tomcat은 더 벌어져서 9.0.65가 아니라 9.0.102였습니다. 트리를 따라가 보니 `tomcat-embed-core:9.0.83 -> 9.0.102`로 강제된 흔적이 있었고, 출처는 배포 모듈 build.gradle의 `ext['tomcat.version'] = '9.0.102'` 한 줄이었습니다. 지난 Tomcat CVE 때 누가 올려 둔 것인데, 스캐너의 `tomcat.version` 정규식이 `ext['...']` 꼴을 못 읽고 있었습니다. 도구가 그 줄을 지나쳤다는 걸 해석 출력과 대조해서야 알았습니다.

같은 출력에서 전이 의존성 73개 좌표가 나왔습니다. Framework 5.3.31 라인에서 28건, 그 밖의 전이 의존성 10개 아티팩트에서 33건이 OSV에 걸렸습니다.

```
### [MEDIUM] OSV-SPRING-FRAMEWORK — spring-framework (해석 결과) 5.3.31: OSV 등재 취약점 28건 (HIGH 10 · MEDIUM 13 · LOW 5)
### [MEDIUM] OSV-TRANSITIVE — 전이 의존성 10개 아티팩트에 OSV 등재 취약점 33건 (CRITICAL 0)
- org.yaml:snakeyaml:1.30 7건; ch.qos.logback:logback-core:1.2.12 8건;
  com.fasterxml.jackson.core:jackson-databind:2.13.5 5건; ...
```

이 숫자는 세 번 바뀌었습니다. 처음에는 전이 항목이 "15개 아티팩트 62건, CRITICAL 1"이었는데, spring-web과 spring-webmvc가 Framework 제품 라인과 전이 목록에 이중으로 잡혀 있었습니다. 그걸 빼니 Framework 라인의 CRITICAL 1건이 리포트에서 통째로 사라졌습니다. 평가기가 Framework와 Boot의 OSV 결과를 조회만 하고 판정 대상에 넣지 않고 있었습니다. 고치고 나서 보니 spring-expression이 아직 전이 쪽에 남아 있었습니다. 중복 제거를 아티팩트 이름 목록으로 하고 있어서였고, groupId를 제품에 매핑하는 방식으로 바꾸자 같은 그룹의 아티팩트 다섯 개가 Framework 라인으로 옮겨 갔습니다. 세 번 모두 리포트 숫자를 다시 세다가 잡았고, 처음 찍힌 숫자는 하나도 남지 않았습니다.

빌드 파일에는 snakeyaml도 logback도 이름이 안 나옵니다. 빌드 파일 추정은 라인까지만 쓰고, 패치 번호와 전이 의존성은 해석 출력을 받아야 합니다. 멀티모듈이면 배포 모듈 기준으로 `./gradlew :app:dependencies --configuration runtimeClasspath > deps.txt`, Maven이면 `mvn dependency:tree -Dscope=runtime -DoutputFile=deps.txt`를 CI 앞 단계에 둡니다.

## 규칙 파일이 제 손에 묶여 있었습니다

두 번째로 틀린 곳은 신선도입니다. 규칙을 데이터로 두면 새 CVE는 JSON 한 항목으로 추가된다고 README에 써 두었는데, 그 항목을 추가하는 사람이 저뿐이라는 뜻이기도 합니다. 제가 2주 손을 놓으면 그동안 나온 CVE는 아무도 못 봅니다. 실제로 규칙 파일은 9월 3일 버전에 멈춰 있었고, 그 사이 Netty와 Tomcat에 CVSS 9.1짜리가 하나씩 나왔습니다.

규칙 파일에서 버전 범위와 수정 버전을 빼고 스캔 시점에 OSV.dev에서 받아오게 바꿨습니다. 파일에는 사람이 판단해야 하는 사용 흔적만 남깁니다. OSV에는 있지만 흔적 정의가 없는 CVE는 제품당 한 줄로 묶어 MEDIUM으로만 냅니다. 2.7 라인 저장소의 Tomcat 9.0.102만 해도 OSV 등재가 29건인데, 처음에 낱개로 나열했더니 리포트가 50줄이 되어 아무도 안 읽을 물건이 됐습니다. 답은 어차피 "9.0 라인 최신으로 올려라" 하나라서 묶는 쪽이 맞았습니다.

OSV도 다 믿으면 틀립니다. Spring이 8월 20일 공개한 Security·GraphQL 권고는 9월 중순까지 OSV에 없었습니다. core, ldap, web, oauth2 모듈을 다 조회해도 0건이라, 규칙 파일 스냅샷이 없었으면 CVSS 9.4를 놓쳤습니다.

OSV는 Tomcat 10.1의 수정 버전을 10.1.58로 적고 있는데, Maven Central에 그 버전은 없습니다. 10.1.57 다음이 10.1.59입니다.

```json
{ "id": "GHSA-gcx9-497g-6cp6", "aliases": ["CVE-2026-65182"],
  "affected": [{ "package": { "name": "org.apache.tomcat:tomcat" },
                 "ranges": [{ "events": [{ "introduced": "10.1.0-M1" }, { "fixed": "10.1.58" }] }] }] }
```

CVE 요약 사이트 여럿이 같은 번호를 안내하고 있어서 어딘가 하나가 틀리면 그대로 번지는 구조였습니다. 이 대조는 도구에 맡겼습니다. 권고 버전을 적기 전에 Maven Central 메타데이터로 존재를 확인하고, 없으면 같은 라인의 다음 버전을 대신 적습니다. 지금은 `10.1.59 (추정: OSV는 10.1.58 표기, Central 미존재)`로 나옵니다. 번호가 건너뛴 릴리스라면 다음 버전이 수정을 담고 있지만, OSV의 수정 버전 자체가 틀렸다면 도구는 엉뚱한 버전을 권고합니다. 규칙 파일에 프로젝트 권고문 기준 수정 버전이 있으면 그쪽을 쓰고, 없을 때만 이 추정으로 떨어집니다.

두 번째 소스로 GHSA를 붙이려다 그만뒀습니다. Maven 생태계에서 OSV의 주 공급원이 GHSA라 위 JSON의 10.1.58도 거기서 온 값이고, 같은 오류를 두 번 받습니다. OSV와 독립인 소스는 상류인 Spring 권고문, Tomcat 보안 페이지, NVD뿐입니다. 8월 20일의 공백을 메운 것도 Spring 권고문이었으니, 다음 버전에서는 Spring과 Tomcat의 권고문 페이지를 직접 긁어 붙일 계획입니다.

지원 종료일도 같은 방식으로 옮겼습니다. endoflife.date를 스캔 시점에 읽게 했더니 두 가지가 드러났습니다. 하나는 제 표의 오류입니다. Spring Security 7.0의 OSS 지원 종료를 저는 2027년 7월로 적었는데 실제는 2026년 12월 31일입니다. 다른 하나는 소스끼리의 불일치입니다. Boot 2.7과 Security 5.7의 종료를 endoflife.date는 2023년 6월 30일로 적고 있는데, Spring 공지는 OSS 지원을 그해 11월 24일까지 연장했고 제 표는 그 날짜였습니다. 어느 쪽이든 3년 전이라 판정은 같지만, 온라인 소스가 항상 더 정확한 것은 아니라는 사례를 하나 더 얻었습니다. 규칙 파일에는 두 날짜를 나란히 적어 두고, 도구는 온라인 값을 쓰되 메모를 리포트에 같이 냅니다.

## 세 저장소에서 나온 것과 제가 내린 결론

프로젝트 이름은 A, B, C로 적습니다. A와 B는 Boot 3.5 라인(3.5.0, 3.5.7), C는 2.7 라인(해석 결과 2.7.18)입니다.

셋 다 8월 20일 Spring CVE 다섯 건의 사용 흔적이 없었습니다. 내장 LDAP도, DPoP도, WebAuthn도, 인가 서버 동의 페이지도, GraphQL 페이지네이션 필드도 쓰지 않습니다. 별건인 Tomcat 보안 제약 우회(CVE-2026-65182, 8월 25일 공개)는 web.xml에 `<security-constraint>`를 직접 쓴 경우에만 발동하는데 셋 다 Spring Security로 인가를 처리하므로 해당 없습니다. 여섯 줄이 전부 INFO로 내려갔습니다.

대신 EOL이 셋 다 HIGH입니다. 3.5 라인 종료(6월 30일)는 알고 있었지만, 3.5가 관리하는 Security 6.5에 8월 20일 CVE의 OSS 수정이 안 나온다는 건 POM을 열고서야 확인했습니다. 3.5 안에서 패치를 올리는 것으로는 해결이 안 되니 4.0.8 이상으로 라인을 옮기는 안건을 올렸습니다. Boot 4는 Framework 7과 Jakarta EE 11이 같이 오는 메이저 이행이라 순서를 정했습니다. A는 레이어드 구조에 모듈 다섯 개라 먼저 올려 장애물 목록을 만들고, B는 헥사고날 아홉 모듈에 지금은 기능 개발이 멈춘 서비스라 재개 시점에 A의 목록을 들고 갑니다.

B를 "노출 0건"으로 두는 건 9월 17일의 스냅샷이지 유지되는 상태가 아닙니다. PR이 없으니 CI의 스캐너도 돌지 않고, 새 CVE가 B가 실제로 쓰는 기능을 건드려도 아무도 모릅니다. B는 현 상태를 동결하고 주 1회 재스캔으로 노출을 감시하되, 안건에는 재개 전까지 이 상태를 허용하는 기간을 연말로 못 박았습니다. 재스캔을 B 자신의 워크플로에 걸지는 않았습니다. 아무도 열지 않는 저장소의 Actions 탭에 결과가 쌓이기만 하고, 스케줄이 어떤 이유로든 멈추면 그 사실을 알아차릴 사람도 없습니다. 매주 결과를 보는 A 저장소의 크론에서 B를 체크아웃해 같이 스캔하도록 했습니다. 3.5 라인은 끝났으니 앞으로 나올 패치는 없고, 재개 전까지 할 수 있는 일은 감시입니다.

C는 계산이 다릅니다. 2.7은 2023년에 끝났고 지금 올리려면 Boot 3 이행(javax→jakarta)을 지나 4.0까지 두 단계입니다. 상용 지원을 사는 선택지도 있지만, 라인 이동 말고는 근본 해결이 없다고 봤습니다. 논거의 첫 줄은 CRITICAL이 아닙니다. 처음 리포트의 CRITICAL 1건은 CVE-2016-1000027, spring-web의 HttpInvoker 역직렬화였는데, 이건 "버전은 범위 안, 기능은 미사용"의 전형적인 사례이고 Spring도 5.3에서 수정하지 않기로 한 건입니다. HttpInvoker 흔적 규칙을 하나 정의하자 INFO로 내려갔고, 안건 문서의 첫 줄을 다시 썼습니다. 지원이 끝난 라인이라 앞으로 나올 모든 CVE에 수정이 안 나온다는 것이 첫 줄이고, 둘째 줄은 Framework 5.3 라인의 28건입니다. Tomcat 29건은 9.0 라인 안에서 올릴 수 있어 라인 이동 논거에서 뺐습니다.

다만 9월 말에 다른 배포가 잡혀 있어 착수는 4분기이고, 그 전까지의 완화 목록에는 jackson, snakeyaml, Tomcat 9.0 최신을 넣었습니다. 이 완화로 지워지지 않는 것도 적어 둡니다. Framework 5.3 라인의 HIGH 10건은 라인 자체의 문제라 라인 이동 전까지 남습니다.

JDK 27 항목은 셋 다 같았습니다. GC 플래그도, 에이전트도, Unsafe도 없습니다. 27이든 29든 올릴 때 확인할 것은 소형 컨테이너에서 Serial이 G1로 바뀌는 것 하나이고, 압축 객체 헤더 충돌 후보는 0건이었습니다.

## 아직 못 하는 것과 다음에 할 것

JEP 534는 깨지는 도구 목록을 제공하지 않습니다. 스캐너의 Unsafe, JOL, lincheck, javaagent 항목은 커뮤니티 이슈를 근거로 한 "확인하라" 신호이지 확정 판정이 아닙니다. 사용 흔적 문자열도 권고문을 읽고 제가 고른 것이라 빠뜨리거나 과하게 잡을 수 있습니다. WebAuthn 규칙이 Yubico의 서버 라이브러리를 Spring WebAuthn으로 잡았던 적이 있어서 그 뒤로는 Spring Security 전용 심볼로만 좁혔습니다.

`ext['tomcat.version']` 정규식 누락은 이 글을 쓰면서 고쳤지만 같은 종류의 누락이 더 있습니다. Kotlin DSL의 `extra[...]`, 버전 카탈로그, `resolutionStrategy.force`처럼 변형은 계속 나오고, 정규식을 늘리는 것으로는 끝이 안 납니다. 다음 버전에서는 빌드 파일 추정을 버리고 CycloneDX SBOM을 입력으로 받을 생각입니다. 같은 이유로 "저장소당 대표 버전"도 배포 아티팩트의 classpath 단위로 바꿔야 합니다. 배포되지 않는 모듈의 낡은 버전이 리포트를 오염시킬 수 있기 때문입니다.

회귀는 픽스처 세 개(취약, BOM 추정, 해석 결과)로 잡고 있었는데, 이번 정규식 건을 겪고 보니 픽스처를 낱개로 늘리는 건 흔적 정의당 하나씩 계속 늘어나는 일입니다. 픽스처별 리포트 전체를 골든 파일로 고정해, 정규식을 고칠 때 다른 판정이 움직이면 diff로 바로 드러나게 바꿨습니다. 골든 파일은 오프라인 판정만 고정합니다. OSV를 실시간으로 조회하는 경로까지 고정하면 다음 주에 새 CVE가 등재되는 순간 코드 변경 없이 깨지고, 그때부터 diff를 아무도 안 보게 됩니다. 온라인 경로는 녹화해 둔 OSV 응답을 스텁으로 넣어 따로 고정했습니다.

다음 버전에서 먼저 할 일은 판정 결과와 판정 불능을 리포트에서 구분하는 것입니다. 휴면 저장소라 도구가 안 돌았거나, 네트워크 오류로 OSV 응답이 비었거나, 잘못된 설정 입력이 들어왔을 때, 그 부재가 "취약점 0건"으로 읽히면 조용한 오류 중 최악입니다. 조회 실패는 UNKNOWN으로 따로 찍고, `--fail-on`은 UNKNOWN도 실패로 봅니다. 이대로 두면 OSV가 잠깐 죽을 때 모든 PR이 깨지고, 보안 스캐너가 빌드 가용성의 단일 장애점이 되는 순간 팀은 `--fail-on`을 끄자고 합니다. 중간 지대를 두었습니다. 마지막 성공 조회를 7일까지 보관하고, 조회가 실패하면 캐시로 판정하되 리포트 머리에 `OSV 조회 실패, 3일 전 캐시 기준`이 찍히고, 8일째부터는 UNKNOWN으로 빌드가 깨집니다.

억제 파일 `.jvmrisk-ignore`에는 만료일과 사유가 없으면 무효이고 만료되면 다시 나오는 규칙을 두었습니다. 한 번 검토하고 영구히 안 보는 목록이 되는 걸 막으려는 것입니다. 규칙 파일의 흔적 정의도 권고문 URL과 발동 조건이 비어 있으면 로딩에서 거부되게 해서, 제가 아닌 사람이 근거를 보고 고칠 수 있게 했습니다. 남은 것은 OSV에만 있는 항목을 규칙 뼈대로 뽑아주는 `--suggest`로 Tomcat의 DIGEST·FORM 인증 CVE 두 건에 흔적을 정의하는 것과 GitHub Marketplace 등록입니다.

코드와 규칙 파일은 [github.com/cloud911948/jvm-risk-scanner](https://github.com/cloud911948/jvm-risk-scanner)에 있습니다.
