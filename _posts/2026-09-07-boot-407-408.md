8월 20일에 Spring이 취약점 91개를 한 번에 공개했습니다. 그중 하나가 Spring Security의 내장 LDAP 서버에 관리자 계정이 고정돼 있고 모든 네트워크 인터페이스에 바인드된다는 것이었고, CVSS 9.4였습니다. 수정 버전은 7.0.7과 7.1.1이었습니다.

수정 버전을 확인하고 나서 Spring Boot가 어느 버전부터 그 Security를 물고 있는지 보려고 spring-boot-dependencies POM을 열었습니다. 4.0.7은 Security 7.0.6을 관리하고, 4.0.8은 7.0.7을 관리합니다. Boot 패치 번호 하나가 취약과 수정을 가르고 있었습니다. 그리고 제가 맡고 있는 서비스들은 4.0 라인이 아니라 3.5와 2.7 라인이었습니다. 3.5가 관리하는 Security 6.5에는 OSS 수정이 없습니다. 3.5 라인은 6월 30일에 지원이 끝났기 때문입니다.

이 사실을 알아내는 데 POM 네 개를 열었습니다. 다음 CVE가 나오면 또 열어야 합니다. 9월 15일에는 JDK 27이 나오는데, 이번에는 GC와 객체 헤더의 기본값이 바뀝니다. 그때도 JEP 두 개를 읽고 서비스마다 JVM 옵션을 뒤져야 합니다. 이걸 사람이 매번 할 일은 아니라는 생각이 들어서, 저장소만 보고 걸리는 것을 알려주는 도구를 만들기 시작했습니다.

## 처음엔 단순한 시작이었습니다

목표는 세 가지였습니다. 런타임과 프레임워크의 지원 종료가 지났거나 임박했는지, JDK 27로 올리면 기본값 변화 때문에 무엇이 달라지는지, 최근 고위험 CVE에 걸리는 버전을 쓰고 있는지. 이 셋을 저장소를 읽어서 마크다운 리포트로 내고, GitHub Action으로 PR에 코멘트를 남기게 하면 됩니다.

Dependabot이나 Snyk가 이미 하는 일 아닌가 싶었는데, 그 도구들은 의존성 버전을 봅니다. JDK 27의 변화는 의존성이 아니라 JVM 쪽에 있습니다. JEP 523은 모든 환경에서 G1을 기본 GC로 만듭니다. JDK 26까지는 CPU가 1개이거나 물리 메모리가 1792MB 미만이면 Serial GC가 자동으로 선택됐는데, 27부터는 같은 환경에서 G1이 뜹니다. 소형 컨테이너로 도는 서비스가 조용히 바뀌는 지점입니다. JEP 534는 압축 객체 헤더를 기본으로 켭니다. 객체 헤더가 96비트에서 64비트로 줄어 힙이 10~20% 줄지만, 객체 레이아웃을 직접 읽는 코드는 깨질 수 있습니다. 이런 것은 `build.gradle`이 아니라 Dockerfile의 `JAVA_OPTS`나 소스의 `sun.misc.Unsafe`를 봐야 압니다.

규칙은 코드에 넣지 않고 JSON 파일 하나에 두었습니다. JDK 27 기본값 규칙 7개, 지원 종료 표 24행, CVE 6건. 항목마다 출처 URL을 붙였습니다. 새 CVE가 나오면 JSON에 한 항목을 추가하면 끝나야 한다고 생각했습니다. 스캐너는 파이썬 표준 라이브러리만으로 썼고, 일부러 문제를 심어 둔 가짜 저장소 하나를 만들어 13개 항목이 전부 잡히는지 확인하는 테스트를 붙였습니다. 여기까지가 첫날 오전이었고, 오후부터는 도구가 틀리기 시작했습니다.

## 만들다 알게 된 것들

첫 번째로 틀린 것은 도구가 아니라 제가 가져온 자료였습니다. Boot 버전별로 관리하는 Security와 Framework 버전이 필요해서 Spring 공식 문서의 의존성 버전 페이지를 AI 요약으로 읽었습니다. Boot 4.0.8이 관리하는 Spring for GraphQL이 1.3.5라고 나왔습니다. Boot 4.0 라인이 GraphQL 1.3을 쓸 리가 없어서 POM을 직접 열어 보니 2.0.5였습니다. 큰 표를 요약기에 맡기면 이런 일이 생깁니다. 그 뒤로는 Maven Central에서 POM을 그대로 받아 필요한 값만 뽑았습니다.

```bash
for v in 4.0.7 4.0.8 3.5.16; do
  pom=$(curl -s "https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-dependencies/$v/spring-boot-dependencies-$v.pom")
  echo "$v | $(echo "$pom" | grep -o '<spring-security.version>[^<]*' | sed 's/.*>//')"
done
# 4.0.7 | 7.0.6
# 4.0.8 | 7.0.7
# 3.5.16 | 6.5.11
```

이 표가 도구의 핵심이 됐습니다. 대부분의 프로젝트는 Security 버전을 직접 적지 않고 Boot에 맡깁니다. Boot 버전만 알면 표에서 Security 버전을 찾아 CVE와 대조할 수 있습니다. 표에 없는 패치 버전이 들어오면 같은 마이너 라인의 인접한 아래 버전으로 채우되, 리포트에 "추정"이라고 표시하게 했습니다. 모르는 것을 아는 척하지 않는 것이 이 도구에서 가장 중요한 규칙이 됐습니다.

두 번째는 실제 저장소에 돌리자마자 나왔습니다. 첫 번째 저장소에서 Spring Boot 버전이 1.9.0이라고 나왔습니다. 그런 버전은 없습니다. 원인은 `p6spy-spring-boot-starter:1.9.0`이었습니다. 이름에 `spring-boot-starter`가 들어가는 서드파티 라이브러리를 Boot 자체로 읽은 것입니다. 그룹 아이디가 `org.springframework.boot`일 때만 Boot 버전으로 인정하도록 고쳤습니다. 같은 저장소에서 모듈마다 Boot 버전이 다르다는 것도 이때 알았습니다. 서른여섯 개 모듈 중 일부는 플러그인으로 2.7.18을, 일부는 의존성에 2.7.3을 직접 적고 있었습니다. 이런 경우 가장 오래된 버전을 기준으로 대조하고, 버전이 섞여 있다는 사실 자체를 별도 항목으로 보여 주게 했습니다.

세 번째는 속도였습니다. 자바 파일 1,700개짜리 저장소에서 `Unsafe` 사용을 찾으려고 파일을 하나씩 읽었더니 3분이 넘어 시간이 초과됐습니다. Windows 파일 시스템을 WSL에서 읽는 환경이라 더 느렸습니다. `grep`이 있으면 `grep`을 쓰고 없을 때만 직접 읽도록 바꾸자 몇 초로 줄었습니다. 도구를 만들 때 표준 라이브러리만 고집했는데, 운영체제에 이미 있는 것을 쓰지 않을 이유는 없었습니다.

## 그래도 못 잡는 것

세 저장소를 돌린 첫 결과는 셋 다 CRITICAL이었습니다. 전부 그 LDAP 취약점이었습니다. 그런데 셋 중 어느 것도 내장 LDAP 서버를 쓰지 않습니다. 버전이 취약 범위에 있는 것과 취약한 코드 경로를 실제로 쓰는 것은 다른 문제인데, 도구는 버전만 보고 있었습니다.

그래서 CVE 규칙마다 사용 흔적 문자열을 추가했습니다. 내장 LDAP이면 `UnboundIdContainer`나 `spring-security-ldap`, DPoP 취약점이면 `DPoPProofJwtDecoderFactory` 같은 것들입니다. 소스와 빌드 파일과 설정에서 이 문자열이 하나도 없으면 심각도를 정보 수준으로 내리고 "취약 버전이나 사용 흔적 없음"이라고 씁니다. 흔적이 있으면 원래 심각도에 발견한 파일을 붙입니다.

```
### [INFO] CVE-2026-59270 — spring-security (Boot BOM 관리) 6.5.6: 취약 버전이나 사용 흔적 없음
- 조건: spring-security-ldap 의 내장(UnboundID) LDAP 서버 사용 시 — 소스·빌드·설정에서 관련 문자열 미발견(조건 미충족 추정)
- 조치: 버전 자체는 취약 범위. 업그레이드 시 함께 해소: 7.0.7, 7.1.1
```

이렇게 고치고 다시 돌렸더니 두 번째 저장소에서 WebAuthn 취약점이 HIGH로 살아남았습니다. 흔적으로 잡힌 파일을 열어 보니 Yubico의 `webauthn-server-core`로 구현한 패스키였습니다. Spring Security의 WebAuthn 모듈이 아니었으니 해당 CVE와는 관계가 없습니다. 흔적 문자열을 `webauthn`처럼 기능 이름으로 잡아서 생긴 일입니다. `org.springframework.security.web.webauthn`과 `.webAuthn(` 같은, 취약한 코드 경로에서만 나오는 심볼로 좁혔습니다. 흔적 규칙은 "이 기능을 쓰는가"가 아니라 "이 취약한 구현을 쓰는가"를 물어야 한다는 것을 세 번째 오탐에서 배웠습니다.

여전히 못 잡는 것도 있습니다. JEP 534는 압축 객체 헤더가 어떤 도구를 깨뜨리는지 목록을 주지 않습니다. `Unsafe`, JOL, lincheck, `-javaagent`를 후보로 잡은 것은 커뮤니티 이슈를 근거로 한 추정이지 확정이 아닙니다. 지원 종료일도 배포판마다 다릅니다. JDK 17은 Oracle 기준으로는 이달 말이지만 Temurin은 내년 10월까지 갑니다. 규칙에 주석으로 적어 두는 것 외에 좋은 방법을 아직 찾지 못했습니다.

## 세 저장소에서 무엇이 나왔나

제가 맡고 있는 저장소 셋에 돌렸습니다. 회사 프로젝트라 이름은 가렸습니다.

| | 구성 | 남은 지적 |
|---|---|---|
| 프로젝트 A | JDK 21, Boot 3.5.0 | Boot·Framework·Security 3.5 라인 지원 종료 |
| 프로젝트 B | JDK 21, Boot 3.5.7, 9개 모듈 | A와 같음. 3.5 최신 패치를 써도 벗어나지 못함 |
| 프로젝트 C | JDK 17, Boot 2.7.3과 2.7.18 혼재, 36개 모듈 | Boot 2.7·Framework 5.3·Security 5.7 지원 종료, JDK 17이 Oracle 기준 27일 뒤 종료 |

CVE는 셋 다 사용 흔적이 없어 정보 항목으로 내려갔습니다. 실제 노출은 없었습니다. 대신 지원 종료가 전부였습니다. 프로젝트 B는 3.5 라인의 거의 마지막 패치를 쓰고 있었는데도 8월 20일 CVE의 OSS 수정을 받을 수 없습니다. 3.5 라인에서 패치를 부지런히 올리는 것으로는 해결되지 않고, Boot 4.0.8로 올려야 합니다. 이 결론은 도구를 만들기 전에는 "언젠가 올려야지" 정도로만 알고 있던 것입니다.

JDK 27 항목은 셋 다 같았습니다. GC 플래그도, 에이전트도, `Unsafe` 사용도 없었습니다. 27로 올릴 때 확인할 것은 소형 컨테이너에서 Serial이 G1로 바뀌는 것 하나뿐입니다. 걱정했던 압축 객체 헤더 충돌 후보는 0건이었습니다. 이것도 도구를 돌리기 전에는 몰랐습니다.

## 마무리

도구를 만들면서 세 번 틀렸고, 세 번 다 "버전은 맞는데 그 뒤가 없었다"는 종류였습니다. 요약이 버전을 틀리게 읽었고, 서드파티 이름을 Boot로 읽었고, 버전만 보고 사용 여부를 안 봤습니다. 고칠 때마다 도구가 아는 척하는 범위를 줄이는 쪽으로 갔습니다. 표에 없으면 추정이라고 쓰고, 흔적이 없으면 정보로 내리고, 모르는 것은 규칙 파일에 모른다고 적었습니다.

정확한 도구보다 정직한 도구가 운영자에게 더 쓸모 있다는 것을 이번에 알았습니다. 여러분의 저장소는 어느 라인에 있습니까. 패치를 올리면 해결되는 자리입니까, 라인을 바꿔야 하는 자리입니까.

코드와 규칙 파일은 [github.com/cloud911948/jvm-risk-scanner](https://github.com/cloud911948/jvm-risk-scanner)에 있습니다. `.github/workflows`에 여덟 줄을 추가하면 PR마다 리포트가 달립니다.
